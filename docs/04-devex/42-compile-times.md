# 42 — Compile Times & the Edit Loop

> ⚠️ **Status: architecture honoured, every number unverified.** The rules this document exists to
> justify — A1 shallow generics at the boundary (no `Router<S>`), A2 erase early (one
> `BoxCloneSyncService` per route, one non-generic `HandlerFn::invoke` per handler), A3 macros emit
> little, A4 concrete `check_*` helpers — are all visible in the shipped code. **None of the budgets
> is measured**: there is no `xtask`, no `bench-compile`, no committed baseline, no CI gate and no
> `examples/bench`. Treat every figure below as a target, not a result.

> This is the row on the scorecard we are most likely to lose. It is therefore a feature
> specification with numeric budgets and an owner, not a page of tips.

## The honest framing

A FastAPI developer's edit loop is ~0 s. Ours will not be. What we can deliver is a loop that is
**fast enough to stay in flow** — a p50 under 3 seconds for the edit people make most often — and
that *never* silently regresses. We say this plainly in the marketing rather than pretending.

## Where the time goes

Three costs, in the order they bite:

1. **Linking.** Dominates incremental rebuilds. Mitigated by a faster linker — `rust-lld` is the
   default on `x86_64-unknown-linux-gnu` as of Rust 1.90, and the compiler-performance team measured
   linking reduced ~7× and end-to-end incremental compilation down ~40% from that change alone.
   `mold` is faster still for large binaries; `lld` is the right default on macOS.
2. **Monomorphisation.** Generic code instantiated per type. This is *our* design problem: a
   framework with `Router<S>`, deeply generic middleware, and type-level query builders generates
   enormous amounts of code.
3. **Proc-macro expansion.** Our derives. Cheap per invocation, expensive at 200 endpoints if we
   are careless.

## Architectural rules (constraints on Moso's own code)

These are the rules that actually move the number. They are enforced by review and by CI budgets.

| Rule | Rationale |
| --- | --- |
| **A1 — Concrete types at the API boundary.** `Router`, `App`, `Error`, `Select<E>` are not generic over user state or clause shape. | The largest single source of monomorphisation in Axum apps is `Router<S>` threading a state type through every layer. |
| **A2 — Erase early.** A handler becomes a `BoxCloneService` at registration; a middleware is boxed once. | Bounds the generic surface to ~40 lines per endpoint regardless of app size. |
| **A3 — Non-generic inner functions.** Every generic public fn is a thin wrapper over a concrete `fn ..._inner(&dyn ..)`. | The classic "outline the body" trick; the generic part is a few lines, the body is compiled once. |
| **A4 — Validation and describe take `&mut ConcreteCtx`.** | Prevents `Validate`/`Describe` from monomorphising per call site. |
| **A5 — Derive output budgets.** `Schema` ≤ 25 lines/field; `Entity` ≤ 40 lines/field; `#[endpoint]` ≤ 60 lines total. | Measured by `xtask expand-size` in CI. |
| **A6 — `syn` used with minimal features**, and macro crates depend on nothing at runtime. | Proc-macro deps are on the critical path of every downstream build. |
| **A7 — No `async_trait` in hot traits.** Use native `async fn` in traits / `impl Future` returns. | Removes a `Box::pin` and a proc-macro pass per method. |
| **A8 — Feature flags actually gate compilation.** Not compiling `moso-orm` for a stateless service is the point. | |

## Budgets (CI gates)

Measured on the reference machine (8-core x86_64 Linux, 32 GB, warm cargo cache) against
`examples/bench` at 50 and 200 endpoints. Every number is recorded per commit and plotted.

| Metric | 50 endpoints | 200 endpoints | Gate |
| --- | --- | --- | --- |
| Cold `cargo build`, default features | ≤ 45 s | ≤ 75 s | M2 |
| Cold `cargo build`, `full` features | ≤ 75 s | ≤ 110 s | M2 |
| Incremental: handler body change | p50 ≤ 2.0 s | p50 ≤ 3.0 s | M2 |
| Incremental: new endpoint added | p50 ≤ 3.0 s | p50 ≤ 4.5 s | M2 |
| Incremental: entity field added | p50 ≤ 4.0 s | p50 ≤ 6.0 s | M2 |
| `cargo check` after handler change | ≤ 1.2 s | ≤ 2.0 s | M2 |
| Growth ratio 50→200 endpoints | — | ≤ 2.4× (sub-linear per endpoint) | M2 |
| `moso-core` alone, cold | ≤ 15 s | — | M1 |
| Release binary size, `full` | ≤ 28 MB | ≤ 35 MB | M3 |

A PR that regresses any budget by > 5% fails CI and must either be justified in the PR description
(which is recorded) or fixed.

## Toolchain configuration (shipped, not documented-and-forgotten)

`moso new` writes `.cargo/config.toml`:

```toml
# .cargo/config.toml — generated by `moso new`
[target.x86_64-unknown-linux-gnu]
rustflags = ["-C", "link-arg=-fuse-ld=mold"]      # falls back to rust-lld if mold is absent

[target.aarch64-apple-darwin]
rustflags = ["-C", "link-arg=-fuse-ld=lld"]

[profile.dev]
opt-level = 0
debug = 1                 # line tables only — full debuginfo is a large link cost
incremental = true
codegen-units = 512

[profile.dev.package."*"]
opt-level = 2             # dependencies optimised once; your crate stays fast to build
debug = false

[profile.release]
lto = "thin"
codegen-units = 1
panic = "abort"
strip = "debuginfo"

# Opt-in, enabled by `moso doctor --fix-config` when the component is present
# [unstable] / cranelift settings are written only when supported by the installed toolchain.
```

`moso doctor` verifies the linker actually took effect (it links a trivial binary and inspects the
build plan) rather than assuming the flag worked — a silently-ignored linker flag is a common,
invisible failure.

**Cranelift** (`rustc_codegen_cranelift`, installable via
`rustup component add rustc-codegen-cranelift-preview`) is offered for dev builds where it is
supported, with the caveat documented: it does not support everything (e.g. `global_asm!`), so
`moso dev --backend cranelift` falls back automatically and says so.

## The app-architecture lever (the biggest one available to users)

Splitting the app into crates bounds what recompiles. `moso generate workspace` performs the split
mechanically (`00-foundations/04`). Measured effect on the reference app at 200 endpoints:

| Layout | Handler-body edit | New endpoint |
| --- | --- | --- |
| Single crate | 3.0 s | 4.5 s |
| Workspace (domain / db / web / app) | **1.4 s** | 2.1 s |

The decision table we publish:

| Project size | Recommendation |
| --- | --- |
| < 30 endpoints | single crate |
| 30–100 | single crate; split if incremental > 3 s |
| > 100, or > 3 engineers | workspace |
| Any size with a heavy pure-logic core | workspace, domain crate first |

## Test compile time

Tests are often the worse loop, because each integration test file is its own binary.

- The generated project puts integration tests in **one** `tests/` binary with modules, not one file
  per resource. This is a large, under-appreciated win.
- `moso test` uses `cargo nextest` (faster runner, better output, per-test isolation).
- `moso-test` is behind a feature so test-only machinery does not compile into the app.

## Docker and CI

The generated `Dockerfile` uses `cargo-chef` so dependency compilation is a cached layer:

```dockerfile
FROM rust:1-slim AS chef
RUN cargo install cargo-chef
FROM chef AS planner
COPY . .
RUN cargo chef prepare --recipe-path recipe.json
FROM chef AS builder
COPY --from=planner /app/recipe.json recipe.json
RUN cargo chef cook --release --recipe-path recipe.json   # cached unless deps change
COPY . .
RUN cargo build --release --bin shop
FROM gcr.io/distroless/cc-debian12 AS runtime
COPY --from=builder /app/target/release/shop /usr/local/bin/shop
USER nonroot
ENTRYPOINT ["shop"]
```

CI guidance in the generated workflow: `Swatinem/rust-cache` for the cargo cache, `sccache` only
where measured to help (its benefit is workload-dependent and it can *slow down* release builds),
`cargo nextest`, and a separate fast `cargo check` job that fails early.

## Measurement harness (build this early — WP-25)

```
xtask bench-compile --scenarios all --json > compile-bench.json
```

Scenarios: cold build, handler-body edit, new endpoint, new entity, `Cargo.toml` touch, test build.
Each runs N times, reports p50/p95, and diffs against the committed baseline. Results are posted as
a PR comment. **This must exist before optimisation work starts**, or the work is guesswork.

`xtask expand-size` runs `cargo expand` on the reference app and reports generated lines per macro,
so a derive that quietly doubles in size is caught in review.

## Hot reload — the honest status

Backend hot-reload in Rust is not a mature, turnkey experience in 2026. Dioxus's `subsecond`
hot-patching is the most promising path and is worth tracking, but the realistic loop today is
`watch + fast linker + fast backend`, giving low-single-digit-second rebuilds rather than
sub-second stateful reload.

Moso's position:
- **Now:** `moso dev` gives a fast, *smooth* restart — request queueing and replay across the
  restart, preserved terminal state, and no dropped connections. The perceived loop is better than
  the raw rebuild time suggests, which is the cheapest available win.
- **Tracking:** a `moso dev --experimental-hotpatch` mode behind a flag once `subsecond` supports
  our shape. We will not promise it in marketing until it works.
- **Alternative under evaluation:** a scripting escape hatch for the innermost loop (e.g. hot-loaded
  templates and policies) — templates and admin views already reload without a rebuild, which
  covers a real slice of edits.

## Acceptance criteria (WP-25)

1. `xtask bench-compile` exists, is reproducible (± 5% across runs), and gates PRs.
2. All M2 budgets in the table are met on the reference machine and published.
3. `moso new`'s `.cargo/config.toml` measurably improves link time; `moso doctor` verifies it took
   effect.
4. `moso generate workspace` on the 200-endpoint reference app produces the improvement in the
   layout table.
5. `xtask expand-size` enforces the per-derive budgets.
6. Growth from 50→200 endpoints is sub-linear per endpoint (≤ 2.4× total).
7. A regression > 5% on any metric fails CI with a chart in the PR comment.
