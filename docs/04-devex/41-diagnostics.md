# 41 - Diagnostics: Killing Trait-Bound Vomit

> **Status: mostly implemented.** `on_unimplemented` on every public trait, `do_not_recommend` on
> every blanket impl, the always-on assertion block, hand-written macro errors with Levenshtein
> suggestions and one-error-per-mistake: all built. The `trybuild` corpus is the **`moso-ui-tests`
> workspace crate**, not a `tests/ui/` directory. ⛔ `moso check` and `xtask check-diagnostics` are
> **not implemented**, which matters: several shipped messages end with "run `moso check`" and that
> advice currently goes nowhere.

> Rust crates that encode invariants in the type system - the Rust RFC that introduced diagnostic
> attributes names **bevy, axum, diesel** specifically - emit trait-resolution errors that are the
> single most cited reason developers bounce off them. Moso treats error quality as a product
> surface with an owner, a budget, and a regression suite.

## The five tools, in order of leverage

| Tool | Applies to | Ceiling |
| --- | --- | --- |
| 1. **API design that avoids the error** | everything | highest - an error that cannot occur needs no message |
| 2. **`#[diagnostic::on_unimplemented]`** | every framework trait | high - covers the known failure shapes |
| 3. **Assertion codegen in macros** | handlers, jobs, middleware | high - moves the span to the user's line |
| 4. **`#[diagnostic::do_not_recommend]`** | blanket impls | medium - suppresses misleading suggestions |
| 5. **`moso check`** | whole-project | medium - catches what types cannot express |

### Tool 1 is the most important and the most often skipped

Design decisions in these documents that exist *primarily* to prevent bad errors:

- **`Router` is not generic over state.** No `Router<S>`, no `FromRef` - this deletes the single
  largest family of Axum trait errors. State comes from the provider map, and a missing provider is
  a *boot* error in prose (`01-http/10`).
- **The query builder is shape-stable.** `Select<User>` never becomes
  `SelectStatement<Filtered<Ordered<...>>>`, so no error ever prints a 40-line type
  (`02-data/21`).
- **One concrete `Error` type.** No `E: IntoResponse` bound to fail (`01-http/16`).
- **Entities do not implement `Schema`.** A structural rule replaces an easy mistake with a
  compile error we wrote ourselves (`00-foundations/04`).
- **Body extractor position is checked in the macro**, not by trait resolution (`01-http/11`).

## Tool 2 - `on_unimplemented` on every public trait

Every trait a user can fail to satisfy carries a hand-written diagnostic. This is a hard
requirement, enforced by a CI check (`xtask check-diagnostics`) that fails if a public trait in a
Moso crate lacks the attribute or an explicit `#[allow(moso::undiagnosed_trait)]` with a reason.

```rust
// spec - the canonical example
#[diagnostic::on_unimplemented(
    message = "`{Self}` is not a valid Moso handler",
    label = "not a handler",
    note = "a handler must be an `async fn` whose parameters all implement `Extract`",
    note = "at most one parameter may implement `ExtractBody`, and it must be last",
    note = "the return type must implement `IntoResponse` - usually `Result<T>` where `T: Schema`",
    note = "run `moso check` to diagnose this handler specifically",
)]
pub trait Handler<M> { … }
```

Traits requiring a diagnostic: `Handler`, `Extract`, `ExtractBody`, `Describe`, `Dependency`,
`Provider`, `Schema`, `Validate`, `Entity`, `Projection`, `Executor`, `SqlType`, `ColumnValue`,
`Job`, `Email`, `AuthUser`, `AuthBackend`, `Policy`, `Guard`, `Config`, `Namespace`, `KvStore`,
`Storage`, `Mailer`, `Bus`, `Migration`.

Type-specific variants use `if()` filters:

```rust
#[diagnostic::on_unimplemented(
    on(Self = "String",
       message = "`String` cannot be a response body on its own",
       note = "return `moso::response::Text(s)` for text/plain, or wrap in a `Schema` type"),
    on(_Self = "Vec<{T}>",
       message = "returning a bare `Vec` produces an unstable API",
       note = "wrap it: `Page<{T}>` for lists, or a struct with a named field"),
    message = "`{Self}` cannot be returned from a handler",
)]
```

## Tool 3 - assertion codegen (always on)

`#[axum::debug_handler]` produces good errors, but only if the user remembers to add it. Moso's
`#[endpoint]` emits the equivalent assertions **unconditionally**, so the span always points at the
user's parameter:

```rust
// generated by #[endpoint]
const _: () = {
    fn _assert_extract<T: ::moso::__private::Extract>() {}
    fn _assert_body<T: ::moso::__private::ExtractBody>() {}
    fn _assert_response<T: ::moso::IntoResponse + ::moso::__private::Describe>() {}
    fn _assert_send<F: ::core::future::Future + Send>(_: F) {}
    fn _check() {
        _assert_extract::<Inject<Db>>();          // span: the parameter's type
        _assert_body::<Json<CreateUser>>();
        _assert_response::<Result<Created<UserOut>>>();
    }
};
```

Cost is measured in CI: budget **≤ 6%** of per-endpoint compile time
(`xtask bench-compile --feature endpoint-assertions`). If it exceeds that, the assertions become
`cfg(debug_assertions)`-only and release builds skip them - a documented fallback, not a default.

The `!Send` future case gets special handling, because it is the worst error in async Rust:

```
error: this handler's future is not `Send`
  --> src/routes/users.rs:14:1
   |
14 | async fn list(Inject(db): Inject<Db>) -> Result<Page<UserOut>> {
   | ^^^^^^^^^^^^^ this future must be `Send` to be spawned by the server
   |
note: `Rc<Cache>` is held across an `.await` at src/routes/users.rs:18
   |
18 |     let cached = rc_cache.get(&id);
19 |     let users = User::query().fetch_all(&db).await?;
   |                                                  ---- `rc_cache` is still alive here
   |
   = help: use `Arc` instead of `Rc`, or drop the value before awaiting:
             let cached = { rc_cache.get(&id) };   // scope ends before the await
```

Achieving the "held across await" note requires cooperating with rustc's existing `!Send` future
diagnostics; the macro's contribution is guaranteeing the *outer* message names the handler and
mentions the fix. **TODO(agent):** measure how much of the inner note rustc already provides on the
target toolchain and only add what is missing.

## Tool 4 - `do_not_recommend`

Blanket impls generate misleading "the following implementations were found" lists. Every blanket
impl in Moso carries `#[diagnostic::do_not_recommend]` so the compiler stops suggesting them as the
fix. In this build that means the **34 `Handler` impls** (1 `EndpointMarker` + 17 `PartsOnly`
arities + 16 `WithBody` arities) plus
`impl<G: Guard> DynGuard for G` and the `CustomLayer` adapter - the `Handler` family is by far the
most important, because without it a handler that fails to compile lists eighteen candidate impls.

The three impls the original text named do **not** exist, and could not:
`impl<T: Extract> ExtractBody for T` is a coherence conflict with the real body extractors;
`impl<T: Schema> IntoResponse for T` and `impl<T: Extract> axum::FromRequestParts for T` are orphan
violations. See `01-http/12-extractors-responses.md` and the implementation note on ADR-0002.

## Tool 5 - `moso check` as the diagnostic of last resort

⛔ **Not implemented.** This is the largest gap in this document, and it is not only a missing
command: `Handler`'s `on_unimplemented` and several boot errors end with "run `moso check` for a
full diagnosis", so the messages currently point at nothing. Either the command lands or those
lines come out.

Some problems are not expressible in the type system. `moso check` covers them
(`40-cli.md` has the lint table). Critically, **`moso check` is suggested by the trait diagnostics
themselves**, so a user facing a confusing error is told where to go.

## The `trybuild` corpus - the regression suite

**As built it is `crates/moso-ui-tests`, a workspace member**, not a `tests/ui/` directory:
`trybuild` needs a real package with its own dependency on `moso`.

This is what makes the commitment real rather than aspirational.

```
tests/ui/
├── handler/
│   ├── body_not_last.rs           + .stderr
│   ├── non_send_future.rs         + .stderr
│   ├── missing_into_response.rs   + .stderr
│   ├── too_many_params.rs         + .stderr
│   └── entity_as_response.rs      + .stderr
├── extract/
│   ├── unknown_extractor.rs       + .stderr
│   └── depends_in_middleware.rs   + .stderr
├── schema/

│   ├── bad_regex.rs               + .stderr
│   └── secret_on_string.rs        + .stderr
├── orm/
│   ├── factory_default_on_field.rs + .stderr   ← the only one of these five that exists
│   ├── wrong_column_type.rs       + .stderr

    └── legacy_path_syntax.rs      + .stderr
```

Rules:
- Every user-facing compile error documented anywhere in `docs/` MUST have a UI test.
- The `.stderr` files are **reviewed like API changes**. A PR that degrades an error message shows
  up as a diff in review, which is the whole point.
- `trybuild` runs on the MSRV and on stable; toolchain-driven changes are noted in the changelog.
- New failure shapes reported by users become UI tests before the fix is written.

## The error-message style guide (normative)

Every Moso-authored diagnostic follows this shape:

```
error: <what is wrong, in plain language, no jargon>
  --> <the user's file:line:col - never a framework file>
   |
NN | <the user's code>
   | ^^^^ <short label>
   |
   = note: <why this rule exists - one sentence>
   = help: <the concrete fix, as code the user can paste>
   = help: <the alternative fix, if there is a common one>
```

Rules:
1. **Name the user's type, not ours.** `CreateUser` - never `<T as Extract>::Output`.
2. **Never print a type longer than 80 characters.** If you would, name the concept instead.
3. **Always give a fix**, as code. "Consider implementing the trait" is not a fix.
4. **One error, not a cascade.** Where a macro can detect a problem, it emits one error and
   suppresses downstream noise by emitting a well-typed placeholder.
5. **Link sparingly.** At most one URL, only for genuinely deep topics
   (`https://moso.rs/e/E0042`).
6. **No blame, no jokes.** People read these while frustrated.

## Runtime diagnostics

Compile errors are half the story. The runtime equivalents:

- **Boot errors** report every problem at once, with source locations and fixes (`01-http/10`).
- **The dev error page** shows the error chain, backtrace with user frames highlighted, matched
  route, resolved dependencies, and the request's SQL statements (`01-http/16`).
- **Validation errors** carry JSON Pointers and stable codes (`01-http/13`).
- **The dev N+1 warning** names the repeated statement and the call site (`02-data/22`).
- **Slow-query warnings** include the plan (`02-data/24`).

## Measuring success

We cannot measure "the error was understandable" directly, so we track proxies:

| Proxy | Target |
| --- | --- |
| Public traits with a hand-written diagnostic | 100% (CI-enforced) |
| Documented compile errors with a UI test | 100% (CI-enforced) |
| Median `.stderr` length in the UI corpus | < 25 lines |
| Longest type printed in any UI `.stderr` | < 80 chars |
| Issues labelled `confusing-error` open > 30 days | 0 |
| Time from a reported confusing error to a UI test | < 7 days |

A standing agenda item in every release review: read three random `.stderr` files aloud. If anyone
has to squint, that is a bug.

## Acceptance criteria (WP-24)

1. `xtask check-diagnostics` fails the build when a public trait lacks `on_unimplemented`.
2. The UI corpus exists with at least the files listed above and runs in CI on stable and MSRV.
3. Every `note`/`help` in the corpus contains a concrete fix (a lint on the `.stderr` files
   asserts a `help:` line is present).
4. Assertion codegen cost is measured and within budget; the `cfg` fallback is implemented and
   tested.
5. `moso check` is referenced from at least the `Handler`, `Extract`, and `Entity` diagnostics.
6. A deliberately broken sample project produces ≤ 3 errors, not a cascade.
