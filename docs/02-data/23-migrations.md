## The model

**Rust entities are the source of truth.** A committed snapshot records the schema as of the last
generated migration. `moso db make-migration` diffs entities against the snapshot and writes a
migration you read before applying.

```
   src/models/*.rs  (#[derive(Entity)])
            │  EntityDescriptor  (generated by the derive)
            ▼
   ┌─────────────────┐   diff    ┌────────────────────────────┐
   │ desired schema  │──────────▶│ migrations/00042_add_x.sql │
   └─────────────────┘           └────────────────────────────┘
            ▲                                  │ apply
   ┌─────────────────┐                         ▼
   │ migrations/     │◀──────── update ──── database
   │  .schema.json   │                    (moso_migrations table)
   └─────────────────┘
```

This is Django's model, not Rails': the diff is automatic, the file is reviewable, and the snapshot
means we never need to introspect a live database to know what we intended. (Cot's stated weakness
is that its auto-generator handles only a small subset of operations; the operation coverage table
below is therefore an explicit acceptance criterion, not an aspiration.)

## CLI

```
moso db make-migration [name]      # diff → write a migration (and update .schema.json)
moso db migrate                    # apply pending
moso db migrate --to 00041         # migrate to a specific version (up or down)
moso db rollback [--steps 1]       # revert
moso db status                     # what's applied, what's pending, what's dirty
moso db redo                       # rollback + migrate the last one (dev loop)
moso db reset                      # drop, create, migrate, seed  (blocked in production)
moso db check                      # does the DB match .schema.json? (CI / deploy pre-flight)
moso db squash --before 00030      # collapse old migrations into one baseline
moso db seed [--file seeds/dev.rs]
moso db migrate --all-tenants      # once per tenant, under a routed tenancy model
moso db shell                      # psql/sqlite3 with the app's connection
moso db explain '<query>'          # EXPLAIN ANALYZE
```

Built as CLI subcommands: `status`, `migrate`, `rollback`, `redo`. The rest exist as one library
call each in `moso_migrate::command` — `make_migration`, `check`, `squash`, `seed`,
`migrate_tenants` — each returning a `serde::Serialize` report so the CLI can drive them over the
existing `--db-*` protocol without linking `moso-migrate`. `reset`, `shell` and `explain` do not
exist in any form.

Two spelling divergences from the sketch above, both deliberate. `command::squash` collapses
*everything* rather than taking `--before`: a partial squash needs the schema as of the cut-off, and
a baseline built from today's entities followed by the migrations that add today's columns fails on a
fresh database. `Squash::over_directory` still takes a cut-off, for a caller who has that schema.
And `command::migrate_tenants` takes the tenant list as an argument rather than discovering it,
because Moso does not know where an application keeps it.

## Migration file format

Default is **SQL**, because SQL is what you review, what your DBA reads, and what you paste into an
incident channel.

```sql
-- migrations/20260729T101500_add_user_locale.sql
-- moso:generated-from .schema.json@a91f2c
-- moso:reversible

-- +migrate up
ALTER TABLE users ADD COLUMN locale text NOT NULL DEFAULT 'en';
CREATE INDEX CONCURRENTLY idx_users_locale ON users (locale);

-- +migrate down
DROP INDEX idx_users_locale;
ALTER TABLE users DROP COLUMN locale;
```

A Rust form exists for data migrations that need application logic:

```rust
// migrations/20260730T090000_backfill_slugs.rs
use moso::migrate::prelude::*;

#[migration]
pub struct BackfillSlugs;

impl Migration for BackfillSlugs {
    const REVERSIBLE: bool = false;
    /// Runs outside a transaction so it can batch without holding locks.
    const TRANSACTIONAL: bool = false;

    async fn up(m: &mut Migrator) -> Result<()> {
        m.batched("select id, title from posts where slug is null", 1000, |rows, tx| async move {
            for r in rows { /* … compute and update … */ }
            Ok(())
        }).await
    }
}
```

## Operation coverage (acceptance table)

The generator MUST handle every row. Rows marked ⚠ require an interactive prompt because the
intent is ambiguous.

| Change in Rust | Generated | Notes |
| --- | --- | --- |
| New entity | `CREATE TABLE` + indexes + FKs | FK ordering topologically sorted |
| Removed entity | `DROP TABLE` | destructive → requires ack |
| New field | `ADD COLUMN` | non-null without default ⚠ (prompts for a fill value) |
| Removed field | `DROP COLUMN` | destructive → requires ack |
| Renamed field ⚠ | `RENAME COLUMN` | prompts: "renamed `name`→`full_name`, or dropped+added?" |
| Renamed entity ⚠ | `ALTER TABLE RENAME` | same prompt |
| Type change | `ALTER COLUMN TYPE ... USING` | lossy conversions require ack + a `USING` expression |
| Nullability change | `SET/DROP NOT NULL` | to NOT NULL: prompts for a backfill if rows exist |
| Default change | `SET/DROP DEFAULT` | |
| New/changed index | `CREATE INDEX CONCURRENTLY` | Postgres: concurrent by default, so it runs outside a tx |
| New/changed unique | `CREATE UNIQUE INDEX` then `ADD CONSTRAINT USING INDEX` | the zero-downtime idiom |
| New FK | `ADD CONSTRAINT ... NOT VALID` + `VALIDATE CONSTRAINT` | two-step to avoid a long lock |
| Check constraint | `ADD CONSTRAINT ... NOT VALID` + `VALIDATE` | |
| Enum variant added | `ALTER TYPE ... ADD VALUE` | must be outside a tx on PG < 12 |
| Enum variant removed | ⚠ | requires a manual plan; generator emits a commented template |
| M2M relation added | `CREATE TABLE` join table + 2 FKs + composite PK | |
| Schema/extension | `CREATE SCHEMA`, `CREATE EXTENSION` | declared via `#[entity(schema=)]`, `app.extensions` |
| Partition declaration | `PARTITION BY` | `#[entity(partition_by = "range(created_at)")]` |

**SQLite** cannot `DROP COLUMN` or alter types in older versions; the generator emits the
12-step table-rebuild recipe automatically and tests it. A rebuild that does not copy a column, or
that narrows a type, is a destructive operation like any other and carries the same gate — the
rebuild is one operation, so the whole of it is emitted commented out.

## Safety policy

Migrations run in production. Moso treats them as such.

1. **Nothing applies automatically, in any profile.** There is no `database.auto_migrate` key and no
   boot hook: a migration runs when a human or a pipeline runs it. What the profile *does* decide is
   rule 2. (An earlier draft of this document specified `database.auto_migrate`; it was never built,
   and "no auto-apply at all" is the stronger guarantee.)
2. **Destructive operations require acknowledgement.** `DROP TABLE`, `DROP COLUMN`, lossy type
   changes, and `TRUNCATE` are emitted commented-out with a header, and `moso db migrate` refuses
   until the developer uncomments them or passes `--allow-destructive`. The generated file says:
   ```sql
   -- ⚠ DESTRUCTIVE: this will permanently delete data in `users.legacy_id`.
   -- Uncomment to apply, after confirming the column is unused by all running versions.
   -- ALTER TABLE users DROP COLUMN legacy_id;
   ```
   A SQLite table rebuild that drops a column, or narrows a type, is gated the same way: the rebuild
   is one operation and the whole of it ships commented out. And in a **production** profile
   `--allow-destructive` is refused outright (`Error::RefusedInProduction`), because the mechanism is
   the committed diff that uncomments the block, not a flag typed at a shell. That is the only thing
   `RunnerOptions::profile` changes on the migrate path.
   The one block no flag can apply is the enum-rewrite template, which has no statements in it:
   `Error::ManualMigrationRequired` says so rather than recording the migration as applied.
3. **Lock guarded.** `pg_advisory_lock` ensures only one process migrates when 20 pods start
   simultaneously. The others wait, then observe the applied state. SQLite has no server to drop a
   dead holder's lock, so its lock is a **leased** row in `moso_migrations_lock` — an owner token and
   an expiry, renewed between migrations and reaped by the next runner once it lapses — which is as
   close to the advisory lock's behaviour as a serverless database gets.
4. **Each migration runs in a transaction** unless marked `TRANSACTIONAL = false` (needed for
   `CREATE INDEX CONCURRENTLY` and `ALTER TYPE ... ADD VALUE`). A failed transactional migration
   leaves nothing behind. A failed non-transactional one marks the version **dirty**, and
   `moso db status` explains exactly what to do.
5. **Checksums.** Applied migrations record a hash. Editing an applied migration is detected and
   refused with a message explaining that you need a new migration instead.
6. **Lock timeout.** Every migration sets `lock_timeout` (default 5 s) and
   `statement_timeout` (default 60 s, overridable per file) so a migration cannot take the site down
   by queuing behind a long transaction. This one default prevents a shocking number of outages.
7. **Expand/contract guidance.** `moso db make-migration` detects patterns that break rolling
   deploys (dropping a column the previous version still writes) and prints the expand/contract
   plan with the two migrations you actually need.

## The `moso_migrations` table

```sql
CREATE TABLE moso_migrations (
  version      text PRIMARY KEY,        -- 20260729T101500
  name         text NOT NULL,
  checksum     text NOT NULL,
  applied_at   timestamptz NOT NULL DEFAULT now(),
  duration_ms  bigint NOT NULL,
  dirty        boolean NOT NULL DEFAULT false,
  applied_by   text                     -- hostname/user, for forensics
);
```

Timestamp-based versions (not sequential integers) so two developers on two branches do not
collide. Out-of-order application is detected and reported; `moso db migrate --allow-out-of-order`
is available and logs loudly.

## `moso db check` — the deploy pre-flight

Compares the live database against `.schema.json` and reports drift in either direction:

```
$ moso db check
✗ database does not match the expected schema

  missing in database:   users.locale (text not null default 'en')
  extra in database:     users.legacy_id (integer)
  index mismatch:        idx_posts_author  expected (author_id) got (author_id, created_at)

  2 pending migrations: 20260729T101500, 20260730T090000
```

Run it in CI against a fresh database (proves migrations reproduce the schema) and in the deploy
pipeline against staging (proves nobody hand-edited production).

## Testing strategy for migrations

Three tests, all in CI, all cheap:

1. **Round-trip.** Fresh DB → apply all migrations → dump schema → compare to a schema built
   directly from `.schema.json`. Proves the migration history reproduces the intended schema.
2. **Reversibility.** For each reversible migration: apply → rollback → apply, then compare dumps.
3. **Idempotence of the generator.** After `make-migration`, running it again produces "no changes."
   A generator that emits spurious diffs is unusable, and this test catches it immediately.

## Seeds

```rust
// example — seeds/dev.rs
#[moso::seed]
pub async fn dev(db: &Db) -> Result<()> {
    let admin = User::factory().email("admin@local").is_admin(true).create(db).await?;
    Post::factory().author(&admin).count(50).create_many(db).await?;
    Ok(())
}
```

Seeds use the same `#[derive(Factory)]` machinery as tests (`04-devex/43-testing.md`), so fixtures
are written once. `moso db seed` is idempotent by convention (upsert on natural keys) and refuses to
run in `production` unless `--force`.

## Acceptance criteria (WP-13)

1. Every row of the operation-coverage table has a test: entity change → expected SQL, for Postgres
   and SQLite.
2. Generator idempotence: `make-migration` twice in a row produces exactly one migration.
3. Rename detection prompts, and `--rename old:new` provides it non-interactively for CI.
4. Concurrent `moso db migrate` from 10 processes applies each migration exactly once.
5. A destructive change is emitted commented-out and blocks `migrate` until acknowledged.
6. Editing an applied migration is detected by checksum and refused with the fix.
7. Round-trip, reversibility, and idempotence tests pass on both dialects.
8. A migration that would hold `ACCESS EXCLUSIVE` beyond `lock_timeout` fails fast rather than
   queuing (tested with a concurrently held lock).
